本地 HMAC 签名 → 换取 AccessToken → 以 Bearer 调用 15 个开放接口。本版依据官方《灵基 OpenAPI 接入指南》补齐全部业务接口的入参、出参与错误码，并按实测修订了对话链路的前置条件。

15 个接口：1 签发 + 14 业务 令牌有效期 7200 秒 签名偏差窗口 ±300 秒 发起对话前必须先建 SSE 连接

1能力范围与接入流程

灵基平台通过 OpenAPI 向第三方系统开放智能对话、资源查询和定时任务执行能力，支持把平台能力集成进业务系统。开放能力受三重约束：应用接口授权、执行用户权限、资源归属。

1.1 四类能力

能力域包含接口典型用途
智能对话与会话管理创建会话、发起异步对话、轮询结果、订阅 SSE、停止执行把智能体嵌入业务单据、审批流、工作台
文件交互上传会话附件、下载会话产物投递报表做分析、取回生成的 Excel / 文档
资源查询智能体、技能、工具、模型列表调用前拿到真实 id / name，避免猜参数
定时任务执行任务列表、触发任务、查询单次执行结果业务系统按自身节奏驱动已有的定时任务

1.2 唯一调用流程

HMAC 是客户端本地完成的签名算法，不是独立 HTTP 接口，平台不存在「先请求一个 HMAC 接口」这一步。整条链路的第一个 HTTP 请求，就是携带 HMAC 签名的令牌签发请求；服务端验签通过后返回 AccessToken，之后全部业务接口用 Bearer 令牌调用。

① 本地计算签名           ② POST /console/openapi/v1/access-tokens        ③ 携带 Bearer 调用业务
   App ID + App Secret  →  验签通过，返回 access_token（7200s）        →  /work/openapi/v1/*
   （Secret 不出本机）        （明文仅此一次返回）                        （14 个业务接口）

1.3 接入四步

  1. 在控制台「开放平台 → OpenAPI」创建并启用应用，配置代理用户、接口授权，打开「允许签发 AccessToken」。
  2. 妥善保存 App ID 与 App Secret（Secret 仅创建或重置时展示一次），通过签发接口换取令牌。
  3. 使用 AccessToken 与租户路由头 X-Tenant-Id 调用已授权接口，按第 9 章对照填写入参、解析出参。
  4. 令牌到期前重新换取；调用异常时通过控制台「调用日志」按 Trace ID / Request ID 定位。
两种凭证不能混用。签发阶段使用 X-Lingee-OpenApi-* 签名头，不携带 Authorization；业务阶段只使用 Authorization: Bearer 与 X-Tenant-Id，不得再携带任何 X-Lingee-OpenApi-* 头或用户身份头。混用会被拒绝，返回 401 与 5001233082。

2接入前准备

准备项说明
目标环境 HTTPS 地址业务接口地址的前缀，例如 https://your-host。调用时在其后拼接相对路径，注意区分两个前缀：签发用 /console，业务用 /work。
租户标识 tenant_id应用所属租户，形如 2559609318685252608_production。签发请求体与 X-Tenant-Id 头都要用，且两者必须一致。
控制台账号需要「开放平台」应用管理权限，用于创建应用、查看调用日志。
App ID / App SecretApp Secret 仅在创建或重置时展示一次，应由调用方服务端安全保存，不进入前端、不写日志、不入代码仓库。
时钟同步签名时间戳默认只允许与服务端偏差 ±300 秒（反重放降级时收紧为 ±60 秒）。机器时间不准会直接导致 401 与 5001233063。
出口 IP如平台配置了 IP / CIDR 白名单，需把调用方出口 IP 或网段报备。该白名单约束 HMAC 签名请求（含签发）。
本文只覆盖 AccessToken 鉴权链路。获取令牌时所需的应用签名属于该链路的必要步骤；业务接口部分只演示 Bearer 调用。

3应用配置

进入控制台「开放平台 → OpenAPI」，点击「创建应用」，填写应用名称（联系人、用途按需），然后完成以下配置。

配置项操作要求
代理用户选择固定用户并指定一个用户，或选择白名单用户并配置允许代理的用户。执行用户由该配置决定，令牌绑定到执行用户。
允许签发 AccessToken打开开关；同时平台侧也须已开启 AccessToken 能力。
接口授权选择接入所需接口，「全部接口」表示授权当前及后续新增接口。授权缺失会在业务调用时返回 403 与 5001233071。
IP / CIDR 白名单约束 HMAC 签名请求的来源 IP（包括 AccessToken 签发及 HMAC 直连）。按需填写出口 IP 或网段，留空表示不限制。Bearer 业务请求当前不逐请求匹配该白名单，但白名单变更会使既有 Token 失效。
应用状态创建后确认应用为启用状态。停用应用会使既有令牌全部失效。

模式执行用户来源签发请求体适用场景

FIXED_PROXY		 应用配置里指定的那一个用户 仅 tenant_id，不得传 subject_type / subject 系统级集成：所有调用都以同一个服务账号身份执行

4令牌签发与 HMAC 签名

4.1 接口地址

POST https://<HOST>/console/openapi/v1/access-tokens

请求体为 JSON，Content-Type: application/json。签发接口无需额外配置接口码授权。

4.2 请求体参数

参数必填说明
tenant_id是应用绑定的租户标识，必须与应用配置一致。
subject_type白名单用户模式必填取值为 mobile、email 或 erp_user。固定用户模式不得传入。
subject白名单用户模式必填手机号、邮箱或 ERP 用户标识，长度 1–256 字符。固定用户模式不得传入。
data_center_idsubject_type 为 erp_user 时必填ERP 数据中心 ID。

固定用户模式（请求体只含 tenant_id）

{"tenant_id":"<TENANT_ID>"}

白名单用户模式（以手机号为例）

{"tenant_id":"<TENANT_ID>","subject_type":"mobile","subject":"13800138000"}

// 邮箱：  {"tenant_id":"<TENANT_ID>","subject_type":"email","subject":"a@b.com"}
// ERP ：  {"tenant_id":"<TENANT_ID>","subject_type":"erp_user","subject":"<ERP_USER>","data_center_id":"<DC_ID>"}
旧版界面的示例曾提示「subject_type 仅支持 mobile / email」，该提示已过时。当前支持 mobile、email、erp_user，其中 erp_user 还必须提供 data_center_id。

4.3 请求头

请求头填写要求
X-Lingee-OpenApi-App-Id应用 App ID。
X-Lingee-OpenApi-TimestampUnix 毫秒时间戳，默认允许与服务端偏差 ±300 秒。
X-Lingee-OpenApi-Nonce每次请求生成新的随机值，建议长度 16–128 字符。重复使用返回 401 与 5001233064。
X-Lingee-OpenApi-SignatureHMAC-SHA256 签名，小写十六进制字符串。
Request-Id必填并参与签名；1–128 个可打印 ASCII 字符，首尾不得有空白。建议 32 位随机十六进制。
X-Tenant-Id应用所属租户标识，用于网关路由，不参与签名。
Content-Typeapplication/json。

4.4 签名原文（canonical）

签名原文由以下 10 行内容以换行符 \n 连接，末尾不追加换行。第 4 行为空（无查询参数），第 9 行为空（不传入内部用户 ID）。

v1                                                  ← 固定版本号
POST                                                ← HTTP 方法，大写
/console/openapi/v1/access-tokens                   ← 完整路径，含 /console 前缀
                                                    ← 空行：Query String 为空
<APP_ID>                                            ← 应用 ID
<TIMESTAMP_MILLIS>                                  ← 毫秒时间戳
<NONCE>                                             ← 随机串
<REQUEST_ID>                                        ← 与 Request-Id 头一致
                                                    ← 空行：User-Id 为空
<BODY_SHA256>                                       ← 请求体 UTF-8 字节的 SHA-256 小写 hex

4.5 计算步骤

  1. 把请求体序列化成最终要发送的那串字节，求 SHA-256，取小写 hex，即 BODY_SHA256。
  2. 按上一节拼出 10 行 canonical（9 个换行，末行后不加换行）。
  3. signature = hex(HMAC-SHA256(appSecret, canonical))，输出小写。
  4. 把 7 个请求头写入并发送。
签完之后不能再动请求。签名一旦算好，不得再修改 URL、Query、请求体或签名相关请求头；任何变动都会让 body 哈希不匹配，返回 401 与 5001233062。如果你在 Apifox 里用了动态占位符（{{$timestamp}}、{{$randomInt}} 之类）填写 Body，一定要在签名前完成变量替换并冻结字节，否则签名与实发内容必然不一致。

4.6 响应

签发成功后，从响应 data 中读取并保存 access_token。

{
  "code": "0",
  "data": {
    "access_token": "lta_...",
    "token_type": "Bearer",
    "expires_in": 7200,
    "expires_at": "2026-09-08T12:30:00Z"
  }
}

access_token 明文仅在签发响应中返回，之后无法再次读取。token_type 固定为 Bearer；expires_in 为剩余有效秒数；expires_at 为 UTC 绝对过期时间。上例时间仅作格式展示，有效期以实际响应为准。

4.7 签名易错点对照

易错点正确做法
签名路径写成 /openapi/v1/access-tokens必须与请求 URL 路径完全一致，含 /console 前缀
canonical 行数按 9 行拼，或末尾多一个换行10 行、9 个换行，末行后无换行；两处空行不可省
时间戳用秒必须毫秒
签名大写 hex小写 hex
对 JSON 对象重新序列化后算哈希对实际发送的那串字节算哈希，算完不得再序列化
发送时多带 Authorization 或 X-Lingee-OpenApi-User-Id签发请求不携带任何用户身份头
以为「租户不参与签名」就可以签后改 bodyX-Tenant-Id 头不参与 canonical，但 body 里的 tenant_id 参与哈希，签后改 body 必然失败

5Apifox 环境与脚本配置

5.1 导入规范文件

在 Apifox 新建测试项目，导入随本手册提供的 灵基开放OpenAPI-v3.openapi.json（或内容完全一致的 .yaml）。只导入其中一个，两份内容等价，同时导入会产生重复接口。

导入后应得到 4 个目录、15 个接口：01 认证 换取 AccessToken、02 业务 资源查询、03 业务 会话、04 业务 定时任务。规范已包含全部业务接口的请求体字段、Query 参数、响应结构与错误码；但不包含可执行脚本——OpenAPI 规范本身不携带前后置脚本，签发接口的签名脚本需要按 5.4、5.5 手工粘贴。

请求体结构在规范中是内联写死的，不通过 $ref 引用组件模型。原因是 Apifox 导入时对 requestBody 里的 $ref 展开不稳定，常见表现就是导入后 Body 页签为空、需要手工一个个补字段。因此导入后 Body 页签应直接列出全部字段；签发与触发任务两个接口还预置了可直接发送的示例（互斥字段只保留一支，避免 403 / 400）。

5.2 环境变量

前置 URL 设置为真实服务源站，例如 https://your-host，不能带 /work 或 /console。然后在环境里填写下表变量。

变量名填写内容
lingee_app_id应用 ID
lingee_app_secret应用 Secret，仅填本地私密值；不要写进共享环境或文档
lingee_tenant_id应用绑定租户，如 2559609318685252608_production
lingee_proxy_modeFIXED_PROXY 或 HEADER_USER，按应用实际配置
lingee_access_token初始留空，由签发接口的后置脚本写入
lingee_token_issued_at初始留空，由后置脚本写入签发时刻（毫秒）
lingee_request_id由业务前置脚本用 {{$guid}} 生成；也可手工填固定值

5.3 认证与脚本的配置位置

位置Auth脚本
签发接口 POST /console/openapi/v1/access-tokensNo Auth，签名通过显式请求头完成签发前置脚本 + 保存令牌后置脚本
14 个业务接口Bearer Token，值填 {{lingee_access_token}}可选令牌检查前置脚本，不计算 HMAC
项目全局避免继承旧认证不安装 HMAC 脚本

每个业务接口保留且仅保留一条 Authorization。若导入后鉴权组件值未自动填充，请手动填写变量引用。No Auth 只表示不使用客户端内置的鉴权生成器，不表示服务端不验签。令牌怎样从签发响应流进 Auth 组件、以及为什么建议在目录级统一配置，见 6.1。

5.4 签发前置脚本

只放在 POST /console/openapi/v1/access-tokens 的前置操作里，位置排在其它所有前置修改之后。脚本会完成变量替换、模式校验、body 哈希与签名。

// 只放在 POST /console/openapi/v1/access-tokens 的前置操作
const C = require('crypto-js');
function env(k) {
  const v = pm.environment.get(k);
  if (!v || /[<>]/.test(String(v))) throw new Error('请配置环境变量 ' + k);
  return String(v);
}
const app = env('lingee_app_id'), secret = env('lingee_app_secret');
const tenant = env('lingee_tenant_id');
if (pm.request.method.toUpperCase() !== 'POST') throw new Error('脚本仅用于签发 POST');
const path = '/console/openapi/v1/access-tokens';
// 前置 URL 必须只有协议、域名及可选端口，不带额外 path。
// 签发接口 URL 固定为上述 path，Query 保持空。
if (!pm.request.body || !pm.request.body.raw) throw new Error('Body 请设置 raw JSON');

if (data.tenant_id !== tenant) throw new Error('Body tenant_id 必须与环境租户一致');
const mode = env('lingee_proxy_mode');
if (mode === 'FIXED_PROXY') {
  // 固定用户：只允许 tenant_id

} else if (mode === 'HEADER_USER') {

    throw new Error('白名单用户需填写 subject_type 和 subject');
  if (data.subject_type === 'erp_user' && !data.data_center_id)
    throw new Error('subject_type=erp_user 时必须提供 data_center_id');
  if (data.subject_type !== 'erp_user' && data.data_center_id)
    throw new Error('仅 erp_user 模式可传 data_center_id');
} else throw new Error('代理模式必须为 FIXED_PROXY 或 HEADER_USER');
pm.request.body.update(body); // 冻结变量替换后的字节，不再二次序列化
const ts = String(Date.now());
const nonce = C.lib.WordArray.random(16).toString();
const rid = C.lib.WordArray.random(16).toString();
const hash = C.SHA256(C.enc.Utf8.parse(body)).toString();
const canonical = ['v1','POST',path,'',app,ts,nonce,rid,'',hash].join('\n');
const sig = C.HmacSHA256(canonical,secret).toString();
pm.request.headers.remove('Authorization');

5.5 保存令牌后置脚本

只放在签发接口的后置操作。签发失败时先清理旧令牌，避免后续业务请求误用过期的值。

// 只放在签发接口的后置操作。失败时清理旧令牌，防止误用
pm.environment.unset('lingee_access_token');
pm.environment.unset('lingee_token_issued_at');
if (pm.response.code < 200 || pm.response.code >= 300) throw new Error('签发 HTTP 失败');
const result = pm.response.json();
const token = result && result.data && result.data.access_token;
if (typeof token !== 'string' || !token) throw new Error('未返回 data.access_token');
pm.environment.set('lingee_access_token', token);
pm.environment.set('lingee_token_issued_at', String(Date.now()));
// 可选：把服务端给出的到期时间也存下来，便于核对本地刷新阈值
if (result.data.expires_at) pm.environment.set('lingee_token_expires_at', result.data.expires_at);

只把令牌保存到当前环境，不打印令牌。超时或后置脚本未执行时，请手动清理旧令牌再重试。

仅配置到业务目录（02 / 03 / 04）的前置操作，不要配置到认证目录。脚本只做本地令牌存在性与保守时效检查，不重复注入认证头。

const issued = Number(pm.environment.get('lingee_token_issued_at'));

  throw new Error('本地保守策略：令牌已超过 115 分钟，请重新签发（服务端有效期 120 分钟）');
pm.variables.set('lingee_request_id', pm.variables.replaceIn('{{$guid}}'));
// Auth 使用 Bearer Token，值为 {{lingee_access_token}}；本脚本不重复注入认证头

115 分钟是客户端建议的保守刷新阈值（约为 10% 剩余有效期），不是服务端限制。官方建议按 expires_in / expires_at 管理，在剩余约 10% 有效期时重新换取。

6Bearer 业务调用

6.1 鉴权组件与令牌的传递机制

先明确一件事：令牌不会被「保存进」Auth 组件。Apifox 的 Auth 组件是一段「生成规则」，只声明用哪种方式鉴权、以及从哪个变量取值；真正存放令牌的是环境变量。三者分工如下。

角色配置位置职责
环境变量 lingee_access_token环境 → 变量（本地值）存令牌明文，是唯一真身
Auth 组件接口或目录的「Auth」页签声明 Bearer 方式，值只写变量引用 {{lingee_access_token}}
后置脚本签发接口的「后置操作」把响应里的 access_token 写进环境变量

完整流转只有一条链路：

签发接口返回 200
  └─ 后置脚本：pm.environment.set('lingee_access_token', data.access_token)
        ↓
   环境变量 lingee_access_token = lta_xxx            ← 令牌真正存放的位置
        ↓
业务接口 Auth = Bearer Token，值填 {{lingee_access_token}}   ← 只是引用，不含明文
        ↓
   发送时 Apifox 先做变量替换，再由 Auth 组件拼出请求头
        ↓
   Authorization: Bearer lta_xxx

为什么不要把令牌直接粘进 Auth

  • 令牌默认 2 小时过期，写死就得每次手工换，十几个接口要改十几遍。
  • 切换环境（测试/生产）或切换执行用户后必须重新签发，写死的值无法自动跟随。
  • 写死的明文会随接口文档导出、分享、进版本库，等于泄露凭证。

两种配置粒度

逐个接口配 Auth 可行，但更省事的是在目录上配一次让子接口继承。建议在「02 业务 资源查询」「03 业务 会话」「04 业务 定时任务」三个目录上分别设置 Bearer Token，值同为 {{lingee_access_token}}；认证目录及其中的签发接口保持 No Auth。这样以后新增业务接口不用再单独配置。

不要在业务前置脚本里再手工写一遍 Authorization。Auth 组件已经会生成这个头，脚本里再 upsert 一次会造成重复头，部分网关直接拒绝。业务侧的前置脚本只做「令牌是否存在、是否临近过期」的检查即可。

签发接口是例外：它不使用 Auth 组件，四个签名头由前置脚本显式写入，所以接口 Auth 设为 No Auth；脚本里还会 remove 掉 Authorization 与 X-Lingee-OpenApi-User-Id，防止继承到目录或项目级鉴权。

6.2 请求头

请求头要求
Authorization必填，格式 Bearer <access_token>。在 Apifox 的 Auth 里选 Bearer Token，值只填 {{lingee_access_token}}，不要再写 Bearer 前缀。
X-Tenant-Id必填，应用所属租户标识，用于网关路由，需与签发令牌时的租户一致。
Request-IdBearer 鉴权层不强制。建议所有 POST 携带用于追踪；仅「创建会话」与「发起异步对话」在提供时作为业务幂等键，须满足 16–128 位 URL-safe（A-Z a-z 0-9 - _ . ~）；其他 POST 不承诺基于该头幂等。不参与签名。
Content-Type发送 JSON 请求体时用 application/json；上传附件用 multipart/form-data。

令牌已绑定执行用户。业务请求不得再携带 X-Lingee-OpenApi-* 签名头或用户身份头；混用凭证会被拒绝。App Secret 不参与此阶段调用。

6.4 令牌缓存与更新

  • 按应用、租户、执行用户三者隔离缓存 Token，不能把某个用户的令牌用于其他用户。
  • 默认有效期 7200 秒，按返回的 expires_in 或 expires_at 管理；建议在剩余约 10% 有效期时重新换取。
  • 不要每笔业务请求都签发 Token。签发有默认限流：同一 appId 与来源 IP 每分钟 30 次、同一 appId 与用户标识每分钟 5 次。
  • 收到 401 与 5001233082 时，先检查凭证混用，再重新换取令牌；仍失败则检查应用和用户配置。

6.5 权限校验不是一次性开关

AccessToken 不绕过接口授权、代理白名单和应用启停。服务端会持续校验应用状态及 Token 绑定的策略版本：应用停用或相关配置（包括 IP 白名单）变更，都会使既有令牌失效，需要重新签发。当前 Bearer 业务请求不会把本次来源 IP 与应用 IP / CIDR 白名单逐请求匹配，该白名单直接约束 HMAC 签名请求。

7通用约定

7.1 统一响应信封

除 SSE 事件流与二进制下载外，其余 JSON 接口共用同一响应信封；各接口文档只描述 data 部分。

{
  "code": "0",
  "message": "",
  "timestamp": 1788850520000,
  "data": { }
}
字段类型说明
codestring"0" 表示成功，其余为错误码。按字符串比较，不要转成数字。
messagestring提示文案，成功时通常为空。
timestampinteger服务端 epoch 毫秒。
dataobject / array业务数据，结构随接口而定；失败时通常为空或省略。

7.2 四条通用约定

  • 空值字段会被省略：响应中的空值字段不下发，调用方必须按「字段可能缺失」处理，不能假定字段一定存在。
  • 时间格式：普通接口统一为 ISO-8601 UTC 字符串，如 2026-09-08T06:55:20Z；SSE 事件内的时间为 epoch 毫秒。
  • 命名风格：请求体字段使用下划线命名（session_id）；分页信封内部字段沿用小驼峰（pageSize、displayName）。
  • 分页：page 从 1 起、缺省 1；pageSize 缺省 50、上限 100，超过按 100 处理且不报错。

7.3 Request-Id 的三种语义

场景是否必填格式语义

9.1 获取 AccessToken

POST /console/openapi/v1/access-tokens

接口 ID：issueAccessToken ｜ 鉴权：No Auth（HMAC 显式请求头）

用 App ID / App Secret 做本地 HMAC 签名，换取 AccessToken。这是整条链路唯一的签发接口，签发环节不需要已有令牌。

签名要点：签名原文由 10 行内容以 \n 连接、末尾不加换行，第 4 行（Query）与第 9 行（User-Id）为空；BODY_SHA256 为实际发送请求体 UTF-8 字节的 SHA-256 小写十六进制；signature = hex(HMAC-SHA256(appSecret, canonical))。签名路径须与请求 URL 路径完全一致，含 /console 前缀。

签名完成后不得再修改 URL、请求体或签名请求头，否则请求体哈希不匹配会返回 401 与 5001233062。本接口不携带 Authorization、X-Lingee-OpenApi-User-Id 等用户身份头。

限流：同一 appId 与来源 IP 每分钟 30 次，同一 appId 与用户标识每分钟 5 次。令牌默认有效期 7200 秒，应按应用、租户、执行用户隔离缓存，不要每笔业务请求都重新签发。

10业务链路

10.1 先取资源，再发对话

发起对话的 assistant_id、skill_names、tools、model 都必须取自资源查询接口的真实返回值，不能凭名称猜。四个查询接口的分工如下。

查询接口返回的 id 填到对话的哪里注意
GET /work/openapi/v1/agentsassistant_id只返回已激活且对执行用户可见的智能体
GET /work/openapi/v1/skillsskill_names 填 name误填 id 会被静默忽略，请求不报错但技能不生效
GET /work/openapi/v1/toolstools 填 id内置 ERP 工具（如 Kingdee-SaaS）也须显式列出
GET /work/openapi/v1/modelsmodel 填完整 id空数组属正常；此时省略 model 用服务端默认

10.2 对话主链路

实测链路：创建会话 → 可选上传附件 → 建立 SSE 连接并保持 → 发起异步对话 → 从流或轮询取结果 → 下载产物；需要中止时调用停止会话。SSE 连接不是可选项，它是发起对话的前置条件。

步骤接口关键取值
① 建会话POST /work/openapi/v1/session响应 data.session_id；可带 external_ref 作为业务键
② 传附件（可选）POST /session/{sessionId}/inbox响应数组里的 inbox_id + filename + mime 原样回传
③ 建立 SSE 连接
（必须先做）		GET /session/{sessionId}/event?event_id=...event_id 必填、8–91 位；连接需持续存活，收到 server.connected 才算就绪
④ 发起对话POST /work/openapi/v1/chat返回 task_id、session_id、event_id，HTTP 202；必须校验响应体 code 为 "0"
⑤ 取结果SSE 流（已连接）
GET /task/{taskId}		流里实时收；也可用 task_id 轮询终态，两者可并用
⑥ 下产物GET /session/{sessionId}/artifact/{artifactId}artifacts 里的 session_id 与 artifact_id
⑦ 中止（可选）POST /session/{sessionId}/stop返回 stopped；无进行中对话时返回 idle
跳过第 ③ 步会直接失败。未建立 SSE 连接、或连接已经断开时，发起对话返回业务码 5001093001，message 为「SSE 路由未注册，请先调用 sse_register」。注意这个错误可能以 HTTP 202 返回——202 只代表请求被受理，不代表执行已启动，所以任何情况下都要以响应体的 code 是否为 "0" 判定成功，不能只看 HTTP 状态。
不要依赖「不传 session_id 自动新建会话」。官方文档说这种写法等价于先调用一次建会话接口，但在「发起对话前必须先有 SSE 连接」的前提下这条路走不通：你没有 session_id 就无法提前订阅，对话会直接返回 5001093001。因此必须显式建会话、再订阅、最后发起对话。

10.3 SSE 是前置条件，轮询是终态兜底

这两个接口常被当成「二选一」，实测不是：SSE 连接必须先建立，否则对话根本发不出去；而轮询不能替代建连，它只是取终态的另一种方式。正确的理解是两者都要、各司其职。

建议实现：先建 SSE 连接负责「看得见」的实时体验，同时用 task_id 轮询兜底终态——流断了、事件漏了，轮询都能补回来。反过来只轮询、不建连接，接口会直接拒绝。

10.4 定时任务链路

定时任务三个接口严格限定在当前执行用户维度：列表只返回该用户创建的任务，触发与查询执行记录都只允许操作本人任务。

  1. GET /work/openapi/v1/scheduled-tasks 取 id（字符串，避免 JS 精度截断）。
  2. POST /work/openapi/v1/scheduled-task/trigger 传 task_id（或 task_name，二选一），拿 run_id。
  3. GET /work/openapi/v1/scheduled-task/{runId} 轮询 status，直到 completed / failed / stopped。
  4. 若返回了 artifacts，用其 session_id + artifact_id 下载产物。
与对话轮询的关键差异：查询单次任务执行结果时，运行中和终态都返回 HTTP 200，不返回 202，也不设置 Retry-After。必须按 data.status 判断是否继续轮询，不能靠 HTTP 状态码判断。

10.5 幂等与重试

  • 只有「创建会话」与「发起异步对话」在携带 Request-Id 时把它当业务幂等键。重试这两个接口时复用同一个 Request-Id才能获得幂等保护；参数不一致会返回 409 与 5001303002。
  • 其余 POST 接口不承诺幂等：停止会话是天然幂等的空操作，但上传附件、触发任务重复调用会重复执行，重试前应先确认上一次是否已生效。
  • 遇到 429（5001303003 并发超限、5001233083 限流）应退避重试，不要立即重发。

11SSE 事件规范

11.1 建连时序（最容易踩错的一点）

event_id 的作用是把「事件订阅」与「后续同一 eventid 的对话」绑定到同一服务实例。实测这条约束是硬的：发起对话前必须已有存活的 SSE 连接，连接断开后同样会失败，必须重连。收到 server.connected 才算真正就绪，在此之前发对话仍可能被拒。

两种常见踩坑：一是先发对话、再连 SSE，必然失败；二是连接建好后闲置过久被服务端或中间代理断开，此时再用同一会话发下一轮，仍会返回 5001093001——而且这一次 HTTP 状态可能是 202，很容易被误判成「提交成功」，直到发现结果一直查不出来。

① GET  /work/openapi/v1/session/{sessionId}/event?event_id=evt-20260908-0001   ← 先连，保持连接
② POST /work/openapi/v1/chat?event_id=evt-20260908-0001                        ← 再发，用同一个 token

event_id 长度 8–91，仅允许 A-Z a-z 0-9 - _ . ~。响应里返回的完整 event_id 通常形如 {session_id}_{原始 token}，可能超过 91 字符——它主要用于服务端粘性路由与排障，不能保证可直接作为重连参数。请始终保留你最初提交的那个 token。

11.2 报文格式

响应 Content-Type 为 text/event-stream，服务端持续推送，不包裹统一响应信封。每条消息以 data: 加一段 JSON 开头、以空行结束；事件类别由 JSON 的 type 字段区分，不依赖 SSE 的 event: 行。

所有事件共用信封 { type, properties }，其中标识字段为小驼峰形式的 sessionID、messageID、turnID。

data: {"type":"message.part.delta","properties":{"sessionID":"34caa001-...","messageID":"msg_abc","partID":"prt_text_01","field":"text","delta":"已完成"}}

data: {"type":"session.idle","properties":{"sessionID":"34caa001-..."}}

  → session.status(idle)

11.5 客户端处理要求

  • session.updated、session.idle、session.status(idle) 都可能重复，须对重复终态做幂等处理，避免重复存储、重复展示或重复触发回调。
  • 收到同一 part 的最终快照（通常带 time.end）后，以该快照的 text 覆盖本地累积值，而不是再次追加。
  • 未知事件 type、未知 part.type 或额外字段应忽略，以保持前向兼容。
  • reasoning 类 part 与文本结构相同，是否展示由调用方决定，但不能拼接到最终回答。
  • artifact 类 part 只提供元数据（artifactId、name、mime、size 等），文件内容须用 sessionId 与 artifactId 调下载接口获取。
  • file 类 part 中的 url 为相对资源路径，仅用于当前事件上下文识别，不是对外下载接口。

11.6 在 Apifox 里验证 SSE

由于对话必须先有存活连接，而 Apifox 不擅长维持长连接，实操上这样分工最省事：在一个终端里用 curl --no-buffer 建连并一直挂着（能持续看到事件输出），然后在 Apifox 里发「创建会话」与「发起对话」。两边用同一个 session_id、同一个 event_id 即可。

curl --no-buffer --request GET \
  "{{BASE_URL}}/work/openapi/v1/session/<SESSION_ID>/event?event_id=evt-20260908-0001" \
  --header "Authorization: Bearer {{TOKEN}}" \
  --header "X-Tenant-Id: {{TENANT_ID}}" \
  --header "Accept: text/event-stream"

Apifox 自己发 SSE 请求时，通常只能看到已缓冲的一段内容，用来确认「连接是否建立、是否返回 200 与 text/event-stream」足够，但验证增量拼接还得靠终端或后端脚本。

需要断言的业务错误：404 与 5001053001（会话不存在或不属于当前执行用户）、5001093001（路由未注册，须先建连或重连后再发起对话）。

14排障

14.1 签发返回 401

  1. 签名路径是否与请求 URL 完全一致，是否包含 /console 前缀。
  2. Query 是否为空（canonical 第 4 行必须为空行）。
  3. canonical 是否为 10 行、9 个换行，末行后无换行，第 9 行是否为空行。
  4. 时间戳是否为毫秒，与本机时钟是否偏差过大。
  5. 签名的 body 字节与实发 body 是否完全一致（是否在签名后又改了请求体或 URL）。
  6. 签名是否为小写十六进制，App Secret 是否使用了重置前的旧值。

14.2 业务返回 401 或 Bearer 被拒

  • 清除全部 X-Lingee-OpenApi-* 头，停用老旧的项目级 HMAC 脚本。
  • 确认只有一条 Authorization，且 Auth 组件没有重复注入。
  • 确认 X-Tenant-Id 与签发令牌时的租户一致。
  • 令牌是否已过期或被配置变更作废——直接重新签发一次。

14.3 变量没有被替换

  • 确认 Apifox 右上角选中的是目标环境，而不是「无环境」。
  • 确认变量名拼写一致，是否存在同名临时变量或路径级变量覆盖了环境变量。
  • 前置脚本里出现 Body 存在未替换变量 报错，通常是 Body 里写了未定义的占位符。

14.4 签发返回 403 与 5001233075

九成是模式与字段不匹配：固定用户模式下 Body 里多了 subject_type / subject；或白名单用户模式下 subject 不在白名单内；或 erp_user 漏了 data_center_id。

14.5 发起对话返回 5001093001

含义很明确：这个会话当前没有存活的 SSE 连接。按顺序排查：

  • 是否在建会话之后、发对话之前调用过 GET /session/{sessionId}/event?event_id=...。
  • 连接是否还在：长连接可能被服务端空闲回收或中间代理切断，发对话前应确认还能收到 server.heartbeat。
  • 是否收到过 server.connected；没收到说明订阅尚未就绪。
  • 是否用了「不传 session_id 自动新建会话」的写法——那种情况你没有 session_id 可以提前订阅，必然失败。
  • 会话标识是否一致：订阅的是 A 会话、发对话传的是 B 会话，同样报这个错。

注意该错误的 HTTP 状态可能是 202，别只看状态码就以为提交成功。

14.6 轮询一直停在 running

  • 确认轮询间隔大于 2 秒，且遵循 Retry-After。
  • 确认查的是同一轮 task_id，不是上一轮的标识。
  • 确认 status 是否已是终态（completed / failed / expired / stopped）。
  • 若返回 404 与 5001053009，说明 task 不属于当前执行用户。

14.7 SSE 收不到事件

  • 建连顺序是否颠倒（必须先连 SSE 再发对话）。
  • event_id 是否严格 8–91 位且只含允许字符。
  • 重连时是否用了响应的完整 event_id（可能超 91 位），应改用最初提交的 token。
  • 客户端是否在 session.idle 之后才判定结束——注意它可能重复。

14.8 用调用日志定位

在控制台应用列表点击「调用日志」，可按接口路径、代理用户、状态、时间范围、Trace ID 或 Request ID 筛选；点击「详情」查看对应调用记录，结合 HTTP 状态与业务错误码定位。向平台报障时请附上这三样信息。

15.3 官方文档未明确、本规范未作假设的部分

为了不虚构字段，以下内容保留为自由结构，仅在字段说明里标注了实际语义：

  • interval_time、once_time（定时任务调度值）的单位与类型。
  • credits（点数消耗）的结构。
  • reasoning（思考过程）在 JSON 接口中的具体结构；SSE 中 reasoning 属于 part.type 的一种。
  • tool_call 的 arguments 与 result 内部结构（随工具变化）。

这些字段在实际联调时按真实返回补充到规范里即可，不影响其余字段的自动补全与校验。
